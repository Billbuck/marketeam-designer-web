L'idee en une phrase

Aujourd'hui, toutes les procedures de generation (PSMD, BAT, vignettes) construisent leur chemin avec Upload code en dur.

La solution : chaque document porte son propre repertoire de travail dans stDocument.Repertoire.
Toutes les procedures utilisent ce repertoire au lieu de recalculer Upload a chaque fois.

En creation : Repertoire = Upload (comme aujourd'hui).
En modification : Repertoire = dossier de l'operation (la ou les fichiers vivent reellement).
En cas mixte (doc existant + nouveau doc) : chaque document a son propre Repertoire.

Pourquoi ca marche dans tous les cas ?

// CREATION : le client uploade un PDF
stDocument.Repertoire = Upload // ← fixe par UploadFichier()
stDocument.EstUploade = Vrai

// SAUVEGARDE : les fichiers sont deplaces
DéplaceFichierUpload() // ← deplace Upload → ROP
stDocument.Repertoire = ROP // ← MIS A JOUR apres le deplacement
stDocument.EstUploade = Faux

// RECHARGEMENT : ChargeDocument remet le bon chemin
stDocument.Repertoire = ROP // ← CheminFichier(IdOpe, __REP_DOCUMENT__)

// MODIFICATION : le client re-personnalise
GenererPsmd...(stDocument) // ← utilise stDocument.Repertoire = ROP
GenererBat...(stDocument) // ← utilise stDocument.Repertoire = ROP
// → les fichiers sont generes LA OU ILS VIVENT

// CAS MIXTE : doc1 existant + doc2 nouveau
tabStDocument[1].Repertoire = ROP // ← doc existant, rechargé
tabStDocument[2].Repertoire = Upload // ← doc fraichement uploade
// → chaque procedure travaille avec LE BON repertoire

Et pour l'enveloppe ?

Meme logique : ajouter un champ stEnveloppe.RepertoireTravail (ou utiliser un existant).
- En creation : = Upload
- Apres sauvegarde / en modification : = CheminFichier(IdOperation, __REP_BAT__)
Les procedures GenererPsmdServeurEnveloppe et GenererBatEnveloppeDepuisPsmd utiliseront ce champ.
1

Creation simple (1 document)

Le client cree une operation, uploade un PDF, personnalise, sauvegarde.

Document 1 — pendant la creation

Repertoire = Upload
CodeTemp = IDContact-DateHeure
EstUploade = Vrai
PSMD, BAT, fonds → Upload

Document 1 — apres sauvegarde

Repertoire = ROP
CodeTemp = IdLettreContenu
EstUploade = Faux
PDF, BAT, fonds → ROP
Rien ne change par rapport a aujourd'hui. Le flux fonctionne deja.
2

Modification — re-personnalisation d'un document existant

Le client rouvre l'operation, clique "Personnaliser" sur son doc, modifie dans le Designer, valide.

Document 1 — au rechargement

Repertoire = ROP/document/
CodeTemp = IdLettreContenu (ex: 42)
PDF = ROP/document/ltr_42.pdf

Document 1 — apres re-personnalisation

PSMD genere → ROP/document/ (au lieu de Upload !)
BAT genere → ROP/bat/ (au lieu de Upload !)
EstUploade = Faux (pas de re-upload)
C'est ici que la correction agit. Les procedures utilisent stDocument.Repertoire = ROP, donc les fichiers sont generes directement au bon endroit. Pas besoin de deplacement.
3

Modification — 1 doc existant + 1 nouveau doc (cas mixte)

Le client rouvre l'operation, garde le doc existant, et ajoute un second document PDF.

Document 1 — existant (rechargé)

Repertoire = ROP/document/
CodeTemp = IdLettreContenu (42)
EstUploade = Faux
PSMD → ROP
BAT → ROP

Document 2 — nouveau (uploade)

Repertoire = Upload
CodeTemp = IDContact-DateHeure
EstUploade = Vrai
PSMD → Upload
BAT → Upload
Chaque document porte son propre Repertoire : pas d'ambiguite. A la sauvegarde, DéplaceFichierUpload ne traite que le doc 2 (EstUploade = Vrai). Le doc 1 est deja au bon endroit.
4

Modification — re-upload d'un document existant

Le client remplace le PDF d'un document existant par un nouveau fichier.

Document 1 — avant re-upload

Repertoire = ROP/document/
EstUploade = Faux

Document 1 — apres re-upload

Repertoire = Upload (ecrase par UploadFichier)
CodeTemp = nouveau IDContact-DateHeure
EstUploade = Vrai
UploadFichier() remet deja Repertoire = Upload et EstUploade = Vrai. A la sauvegarde, le fichier sera deplace vers ROP normalement. Aucun conflit.

1. GenererPsmdServeurDocument() — PSMD au bon endroit

1 ligne ▶
AVANT :

APRES :
sRepTravail = stDocument.Repertoire // stDocument.Repertoire = Upload en creation, ROP en modification
Puis remplacer sRepUpload par sRepTravail dans toute la procedure (sCheminPsmd, sCheminJsonTemp). Le reste ne change pas : sCodeTemp = stDocument.CodeTemp fonctionne dans les deux cas.

2. GenererBatDocumentDepuisPsmd() — BAT au bon endroit

1 ligne ▶

APRES :
sRepTravail = stDocument.Repertoire
Puis remplacer sRepUpload par sRepTravail. Le PSMD est deja lu depuis stDocument.CheminPsmdTemp (chemin complet) : pas de souci. Le BAT sera ecrit dans le bon repertoire.

5. GenereVignetteDocument() — vignettes fond Ghostscript

Ajout parametre ▶
AVANT :
sRepertoirePhysique = cpProjet.__sRepRacine + cpProjet.__sRepUpload + "\" sCheminRelatif = cpProjet.__sHttpMarketeam + cpProjet.__sRepUpload + "/" // Toujours Upload, en dur

En ajoutant des parametres optionnels avec valeur par defaut = Upload, le code existant (appels en creation) continue de fonctionner sans modification. Seuls les appels en contexte modification passent le chemin ROP.

La regle d'or

Ne jamais construire un chemin de repertoire "en dur".
cpProjet.__sMarketeamRepRacine + cpProjet.__sRepUpload → interdit

Toujours utiliser le repertoire qui vit dans la structure.
stDocument.Repertoire → la source de verite
